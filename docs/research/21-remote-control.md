# 21 — Remote control of the OP-XY: how the "agent programs a sequence" demos work, and whether remote keys exist on current firmware

> Research note for the OP-XY Agent. Written 2026-09-26 by a research agent. **Nothing was sent to
> the device.** Builds on `20-midi-control.md` §7 [MIDI20] and the owner's device session 1 in
> `90-device-probe.md` [PROBE] (OS 1.1.33: CC106/107 dead on channels 1 and 16; CC102, CC104 and
> CC105 work). Raw snapshots of every page used are in `research/web/remote/` (git-ignored). Source
> keys like **[VIBE-YT]** resolve in the Sources table at the end. All text is our own summary;
> quotes are kept to a few words.

**Mechanism codes** used throughout (from the brief):

| code | mechanism                                                                                   |
| ---- | ------------------------------------------------------------------------------------------- |
| (a)  | host-side sequencing: the computer plays notes/CCs live; nothing is stored on the OP-XY     |
| (b)  | the OP-XY records incoming MIDI into its own sequencer (live or step record)                |
| (c)  | `.xy` project files are written offline and copied over (MTP / Field Kit)                   |
| (d)  | remote key presses (CC106/107 or similar)                                                   |
| (e)  | something else: SysEx project editing, MMC, NRPN, physical button pushers, camera feedback… |

## 1. TL;DR

- **The demo the owner most likely saw does not press any keys.** Kevin Morrill's _Vibe-Coding
  Beats: AI + OP-XY Workflow_ (YouTube, 2025-09-17) — which OpenAI showed on a slide in its DevDay
  2025 "Developer State of the Union" — is **host-side sequencing (a)**: Codex edits a JSON loop
  and a Python "conductor" streams notes and CCs to the OP-XY over USB MIDI while it plays. Nothing
  is written into the OP-XY's patterns; the repo (`kmorrill/op-xy-vibing`) never sends CC102–107
  [VIBE-YT][VIBE-REPO][DEVDAY-X].
- The same author's other "an AI wrote the whole song" videos run on **other hardware** through
  SysEx project upload (e): the EP-40 Riddim (Claude + `ep-series-sysex`, 2026-07-11) and the
  Elektron Analog Rytm (2026-02-19) [RIDDIM][RYTM]. The OP-XY has no known project SysEx (its TE
  FILE interface only exposes `drum/` and `synth/` [PROBE]).
- **In 2026, a whole song gets into the OP-XY as a file (c).** `kmorrill/xy-format` decodes the
  `.xy` format; its author tells people to point Claude Code or Codex at the repo to turn any MIDI
  file into a project [OPF-31689]. Front ends: tonicmidi.com (XY Workbench), XYBuddy, opxy.app.
  Transfer is MTP / Field Kit [XYF][TONIC][XYBUDDY][OPXYAPP].
- **Recording incoming MIDI (b) works, but a human arms record.** Every harness we found — xy-format
  (Feb 2026, 8 tracks in one pass), antiero's 16-pattern harness (Jul 2026, so ≥ 1.1.15), euxy
  (Jul–Sep 2026), a Reaper user (Feb 2026) — has the person press record + play (or hold record);
  the computer only sends transport, clock and notes [XYF-HARNESS][XYF-16PAT][EUXY][OPF-29710].
- **Remote keys (CC106 down / CC107 up) are a ≤ 1.0.21 feature as far as any source can show.**
  The discoverer's own sheet says it was disabled in 1.0.25; four independent users on 1.0.25–1.0.50
  got no response; in Nov 2025 the discoverer wrote that TE cut it and you must roll back to 1.0.21;
  a user asked TE support to restore it in Mar 2026; the Jul 2026 wishlist summary still asks for
  CC access to the mode buttons and M1–M4; the owner's 1.1.33 test was negative. The only positive
  write-up after 2025 (dawless-reference, sweep dated 2026-03-04) **does not state the firmware**.
  **No source reports any remote-key path on ≥ 1.1.15.** TE has never documented CC102–107.
- **What does work remotely on 1.1.33:** transport (`FA`/`FC`, CC104/105), track select (CC102 on
  channel 1), tempo/groove/scene/project CCs (CC80–86), mutes and parameter CCs [PROBE][TE-MIDI].
  OP-Z heritage points at two **untested** cousins: CC102 on **channel 2** (OP-Z "parameter page"
  0–3, i.e. maybe M1–M4) and **CC103** (OP-Z pattern select; 16 = next, 17 = previous) [OPZ-MIDI].
- **Recommendation:** build "program a sequence" on (c) `.xy` + MTP and on guided (b) takes, keep
  (a) for jamming, and treat remote keys as a probe-gated capability. A ~20-minute owner session
  running §6 H1–H9 (CC102 ch2, CC107 value 1, CC106 as 127/0, CC103, a small CC sweep, MMC) would
  settle the remaining doubt.

Two clues about how TE built this:

- **OP-Z lineage.** CC102 on channel 1 is exactly the OP-Z's "active track" UI CC; the OP-XY
  number was found by a user who simply tried OP-Z CCs [OPF-28351]. On the OP-Z the same CC on
  channel 2 selects the parameter page (0–3), and CC103 selects patterns (0–15 per track, 16 next,
  17 previous) [OPZ-MIDI][OPF-OPZ]. If the OP-XY inherited CC102, it may have inherited the rest.
- **Button-like CCs exist on 1.1.33.** A 1.1.33 user found that CC83/84 (previous/next scene) only
  hold while the value stays non-zero, and that CC85's value-to-scene mapping shifts with the
  number of scenes [OPF-31914]. That is how a held key behaves. If other CCs are "virtual keys",
  a press needs value > 0 and a release needs 0 — the owner's test never sent that pattern.

The second community sheet ("OP-XY - Midi CC implementation", in circulation by 2025-01-09 and
merged into midi.guide on 2026-02-03) is where CC104/105/107 come from [SHEET-2][MIDIGUIDE]. It was
written in the ≤ 1.0.21 era, when CC107 = key up; a release of value 1 (the tempo key) would open
the tempo page, which fits its "View Tempo page" label.

## 5. Conclusions

1. **How the demos program sequences.** The widely seen OP-XY + agent demo (Morrill, Codex) is
   (a) host-side playback. In 2026 the community's route to a full on-device song is (c) — an
   agent writes `.xy` with xy-format and the user copies it over MTP. (b) human-armed recording of
   streamed MIDI is well established. Physical button pushers (e) exist as a workaround. SysEx
   project editing (e) exists only for the EP series and the Rytm. **None uses remote keys on
   1.1.x.**
2. **Remote keys on ≥ 1.1.15: no evidence from any source**, and a verified negative on 1.1.33 for
   the documented encoding. On 1.1.0–1.1.4 the record conflicts. TE has never documented or
   announced CC102–107, so they can change silently with any update.
3. **The OP-XY's remote surface on 1.1.33** is: per-track notes and CCs, transport (`FA`/`FC`,
   CC104/105), track select (CC102), tempo and groove, scenes (mind the CC85 offset quirk reported
   on 1.1.33), project load (CC86, dangerous), and outbound controller mode.
4. **For our agent, in order of usefulness:**
   - _Program a whole song:_ write `.xy` (our M6 work; needs the 1.1.33 layout, whose header was
     bumped [PROBE]) and transfer it over MTP. Our own code already opened an MTP session, and
     closing the session returns the unit to MIDI mode [PROBE]; entering MTP still needs the owner
     (COM → M4) until Field Kit's SysEx for it is captured (`30-presets-samples.md` §6).
   - _Record a take:_ a guided human arm (record + play), then the agent sends transport plus notes
     on channels 1–8 with project channels set to 1–8. CC automation becomes p-locks only in
     hold-record mode (xy-format finding, [MIDI20] §4.5).
   - _Jam:_ host-side sequencing, as in op-xy-vibing.
   - _Keys:_ keep `remoteKeys` probe-gated, record the result per OS version, and re-run the probe
     after each update (it costs seconds).
5. **Rolling back to 1.0.21** brings CC106/107 back according to the discoverer, but loses every
   1.1.x feature (16 patterns, templates, monitor, slicing, sound link…), changes the project
   format and risks the owner's content. Not recommended on the owner's only unit; at most on a
   spare.

## 6. Test list for the owner's unit (OS 1.1.33)

**Ground rules** (as in [PROBE]): owner present; a new empty scratch project; every step
announced; one message group at a time; stop at the first unexpected effect. Settings: stock COM →
midi with clock = both (as left after session 1), echo off. Our tool logs everything the device
sends — `FA`/`FC` show that play/stop happened. After every test the owner presses any key to make
sure nothing is latched (shift, record), and panic is ready: `Bn 7B 00` + `Bn 78 00` on all
channels, then CC105 twice. `research/device/spike.py` can send all of this (`cc`, `rk`, `raw`); its
guard blocks only TE SysEx and CC86, so the MMC frames in H9 go through `raw`.
