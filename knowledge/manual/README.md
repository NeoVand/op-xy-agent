# Our OP-XY manual

This folder is the project's own manual for the teenage engineering OP-XY: reworded, atomic and
built for an AI agent, a search box and the replica's teaching animations. TE's contacts are happy
for us to use the guide's content **as long as it is reworded** (`docs/DECISIONS.md` D2), so:

- the verbatim scrape in `knowledge/official/` is **source material only** — git-ignored, never
  committed, never shipped, never pasted here;
- everything in this folder is **written in our own words**, cites where each fact comes from, and
  ships with the app.

Reference firmware is **OS 1.1.33**; TE's online guide describes **1.1.15**, so changelog entries
after 1.1.15 are errata the manual must layer on top (`docs/DECISIONS.md` D3).

## Layout

```text
knowledge/manual/
  README.md                  this guide (voice, format, workflow)
  units/<area>/<slug>.md     one unit per file: YAML front-matter + a short Markdown body
  build/                     generated by scripts/build-manual.mjs — committed, never hand-edited
    manual.json              validated units for the app (src/lib/manual loads it)
    manual.md                the prompt bundle: the whole manual for the agent's cached system prompt
    search-index.json        MiniSearch index (titles, aliases, summaries, goals, facts)
    coverage.json            which of TE's guide sections the units cover (rewritten only with the scrape)
  verbatim-allow.json        optional: phrases the verbatim guard may accept (see below)
```

Areas (folders), in the order the prompt bundle presents them: `basics`, `hardware`, `sequencer`,
`players`, `instrument`, `sampler`, `auxiliary`, `fx`, `arrange`, `mix`, `project`, `tempo`, `com`,
`howto`. `AREA_INFO` in `src/lib/manual/schema.ts` lists which guide chapters feed each area.

## Why YAML front-matter (and our own parser)

Units are Markdown files with YAML front-matter because the manual is mostly **prose that people
and agents write and review**: a fact on one readable line, a body that is real Markdown, diffs that
read like text, and GitHub rendering the file nicely. Pure JSON units were the alternative (no
parser to maintain), but prose in JSON strings — escaped quotes, no comments, bodies as arrays of
paragraphs — makes writing and reviewing ~170 units noticeably worse, and that is where the effort
goes.

The project adds no dependencies for this, and a full YAML library would be a liability anyway:
YAML's implicit typing turns `1.10` into the number 1.1 and `off` into `false`. So
`src/lib/manual/yaml.ts` is a small, strict, fully tested **subset** parser:

- block mappings and lists, `'single'` / `"double"` quotes, `[flow, lists]` and `{ flow: maps }`
  (also broken over lines, the way Prettier prints long ones), `|` / `>` block scalars, comments on
  their own line;
- plain values stay **strings** unless they are `null`, `true`/`false` or an integer, so versions,
  `off`, `yes` and `0x1F` are always text;
- anything outside the subset (anchors, tags, tabs, duplicate keys, `: ` or ` #` inside an
  unquoted value, multi-line plain values) fails with `line:column` and the fix.

Prettier formats unit files like any other Markdown (it rewrites the YAML's quotes and breaks long
lists); the parser accepts everything it produces. Run Prettier on units before committing.

## Anatomy of a unit

A **unit** is one topic an agent answers about: roughly one guide section, or one sub-feature with
its own controls (a synth engine, a step component, an effect, a how-to, a changelog-only feature).

```yaml
---
id: sequencer.parameter-locks # <area>.<slug>, must match the file path
title: Parameter locks # ≤ 80 characters
aliases: [p-lock, plock, step automation] # what users call it (search + synonyms)
area: sequencer # the folder
order: 30 # optional: position within the area (default 100; overviews 0–10)
context: # optional: where it applies
  modes: [instrument, auxiliary] # instrument | auxiliary | arrange | mix
  screens: [M1, M2, M3, M4] # see SCREENS in schema.ts
summary: Store a module-page value on individual steps; … # 1–2 sentences, ≤ 300 characters
status: current # current | outdated-in-guide | changelog-only | unverified
firmware:
  min: '1.0.9' # first OS release with the feature
  changed_in: ['1.1.21', '1.1.33'] # = every firmware_min below that is newer than min
  guide_version: '1.1.15' # null when the unit cites no guide page
  verified_on: null # OS version on which the owner's unit confirmed the whole unit
facts: # atomic claims, each with one source
  - id: record
    text: To lock a value, keep a step held and turn an encoder; …
    source: https://teenage.engineering/guides/op-xy/sequencer#step-sequencing
  - id: rotate
    text: Shifting a track's sequence with `Tn + [-]/[+]` moves the locks together with the notes.
    source: https://teenage.engineering/downloads/op-xy#1.1.21
    firmware_min: '1.1.21' # required when citing a release newer than firmware.min
procedures: # how-tos the replica can animate
  - id: add
    goal: Lock a parameter value on one step
    preconditions: [the track is selected]
    steps:
      - keys: step n + turn E1…E4 # canonical key grammar (see below)
        note: keep holding the step while turning
        # set: { param: amp decay, value: 25 } # recipes only: what the step sets (see below)
    result: The step plays back with the new value from now on.
    source: https://teenage.engineering/guides/op-xy/sequencer#step-sequencing
parameters: # encoder assignments on a screen
  - screen: M1
    encoder: E1 # E1–E4 = dark gray, mid gray, light gray, white
    layer: base # base | shift | alt (page an encoder click switches to) | click | shift-click
    name: shape
    range: 0–100 # optional, display units
    default: '50' # optional
    cc: 12 # optional; checked against the CC lane model for instrument/aux pages
    note: waveform of the oscillators
    source: https://teenage.engineering/guides/op-xy/synth-engines#prism
related: [sequencer.step-components] # unit ids; must exist
---

The body: a short explanation in our own words (≤ 180 words) — the idea, when to use it, how it
fits with other features. Facts carry the claims; the body connects them.
```

Every fact, procedure and parameter may also carry `verified_on` (the OS version the owner's unit
showed it on) and `confidence` (`official`, `verified`, `measured`, `community-verified`,
`community`, `derived`, `speculative`, `conflicting` — the scale in
`src/lib/core/opxy/common.schema.ts`). The default is `verified` when `verified_on` is set,
`official` for TE sources; any other source needs an explicit confidence.

### Status legend

| status              | meaning                                                                                             | rule the build checks                          |
| ------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `current`           | the guide describes it and still matches OS 1.1.33 (we may add detail)                              | cites at least one guide page                  |
| `outdated-in-guide` | the guide describes it, but a later release changed it in a way the guide misses                    | a guide page, plus a `changed_in` after 1.1.15 |
| `changelog-only`    | the guide is silent about the feature; the OS changelog documents it (guide pages may give context) | cites the changelog entry                      |
| `unverified`        | from community sources or our inference, not yet confirmed                                          | never has `firmware.verified_on`               |

### Firmware tags

- `firmware.min`: the release that introduced the feature (`1.0.9` for launch features).
- `firmware_min` on an item: when that one claim became true, if later than `firmware.min`. A fact
  that cites the changelog entry of a newer release must carry that release as `firmware_min`, and
  behaviour newer than the guide (after 1.1.15) cannot cite the guide.
- `firmware.changed_in`: exactly the set of item `firmware_min` values newer than `firmware.min`,
  oldest first (the build prints the expected list if it is wrong).
- `verified_on`: only for things observed on the owner's unit, citing the probe log
  (`docs/research/90-device-probe.md`). Never guess it.

## Voice and style

**Our own words, always.** Read TE's section, close it, then write what you understood. Do not
translate TE's sentences one by one, do not keep their sentence order and swap synonyms, do not copy
captions. The build fails on any run of **8 or more consecutive words** that also appears in TE's
text (case, punctuation and apostrophes ignored). Short technical names are fine (`sync24`,
`skip parameter lock`); sentences are not.

Tone: plain, exact and a little TE-flavoured.

- Control names in lower case as printed on the unit: shift, com, bar, record, player, M1, T3.
  Normal sentence case otherwise.
- Second person, present tense, short sentences. No marketing ("amazing", "perfect for"), no
  exclamation marks, no emoji.
- One claim per fact, one or two sentences, understandable on its own (no "it" pointing at the
  previous fact). Put conditions in the fact ("with clock set to both, …").
- Say what the unit does, then what you see or hear. Name the page (`com → M1`, "the bar menu").
- Numbers: digits, en-dash ranges (0–127, 40–220 BPM), units spelled as the screen shows them.
- Uncertainty is information: write "not confirmed on a unit", set a confidence, or leave it out.
  Never fill gaps from memory of other devices.
- Do not reproduce TE's typos and copy errors (`docs/research/40-official-docs.md` §5.3); state
  the correct fact and cite the section.
- Product names: "OP-XY" (ASCII hyphen) in our text; TE's "OP–XY" only inside quotes of UI text.

### Key combos

Key combos use the grammar of `src/lib/core/opxy/keys.ts` in its **canonical spelling** (the
build prints the canonical form when yours differs):

| write                                  | means                                                                |
| -------------------------------------- | -------------------------------------------------------------------- |
| `shift + M1`                           | hold shift, press M1 (every key but the last is held)                |
| `record + play → play`                 | press the chord, release, then press play                            |
| `shift + steps → + natural`            | `→ +` keeps the earlier keys held                                    |
| `hold com`                             | long press                                                           |
| `turn E2`, `click E4`                  | rotate / push an encoder                                             |
| `step n + turn E1…E4`                  | ranges with `…`; placeholders `Tn`, `step n`, `key`, …               |
| `[-]/[+]`                              | alternatives with `/`; minus and plus are `[-]` / `[+]`              |
| `key F#3`, `natural 3`, `accidental 0` | a keyboard key by note, or white/black key by number (from the left) |

In YAML, quote key combos that start with `[` (`keys: '[-]/[+]'`) and text that starts with a
backtick. In prose (facts, summary, notes, body), **backticks are reserved for key combos and
control names**: every `code span` must parse (`E1`, `T1…T8` and `volume` name controls). Write
file names, menu values and MIDI bytes as plain text.

Whenever the text means a key, put it in backticks, even on its own (`M3`, `T5`, `step 5`,
`E2`): the site and the chat draw it as the device's own key (the OP-XY prints digits and
pictures, never "M3" or "T5"), and pointing at it rings it on the replica. The track itself
("track 5") and the page ("the filter page") stay words.

### Citing sources

Each fact, procedure and parameter cites exactly **one** source:

- **Guide**: `https://teenage.engineering/guides/op-xy/<chapter>#<anchor>`, with TE's anchor as
  their site writes it (some contain spaces, written `%20`; some are odd, like
  `synth-engines#arrange` for the synth-engine intro). Content with no anchor of its own (e.g. the
  step-component list) is cited by the bare chapter URL. With the scrape present, the build checks
  that the anchor exists and lists the valid ones if not.
- **Changelog**: `https://teenage.engineering/downloads/op-xy#<version>` — except 1.0.29, which TE's
  page anchors as `#1.0.28`.
- **Other TE pages**: product page, field kit guide, sound packs page.
- **Our research**: `docs/research/<note>.md#<github-heading-slug>` — the probe log for anything
  verified on the device, other notes for measurements and derived facts (with a confidence).
- **Community**: any https URL, with `confidence: community` (or `community-verified`).

### Size budget

The whole bundle goes into a cached system prompt, so keep units lean: summary ≤ 2 sentences, body
≤ 180 words (the build warns above), usually 3–15 facts (overview units up to ~30). Split a unit
that grows past that. Target for the finished manual: roughly 170 units and a bundle well under
100k tokens, i.e. **about 500 tokens per unit on average** — the build prints the bundle size and
the per-unit average. The six exemplar units are deliberately rich (~1.3k tokens each); most units
should be much smaller.

## Unit shapes

| shape          | example                            | typical content                                               |
| -------------- | ---------------------------------- | ------------------------------------------------------------- |
| overview       | `hardware.layout`                  | many short facts, simple navigation procedures, `order: 0`    |
| feature        | `sequencer.parameter-locks`        | facts with firmware history, 2–5 procedures                   |
| concept + list | `sequencer.step-components`        | how it works, the list, add/remove procedures                 |
| screen/engine  | `instrument.engine-prism`          | a `parameters` table (+ CCs where the lane model applies)     |
| settings       | `com.midi-settings`                | verified device facts, navigation procedures, settings screen |
| changelog-only | `instrument.save-to-same-snapshot` | changelog facts, unconfirmed gestures marked `derived`        |
| recipe         | `howto.pluck`                      | one goal, ordered procedures, links to the feature units      |

### Recipes the agent can run

A sound-design recipe (`howto.pluck`, `howto.sidechain-duck`) marks each step that sets a value
with `set: { param, value }`, named the way the agent's `plan_steps` tool takes it (`amp decay`,
`lfo type` → `duck`, `cutoff`; the navigator's `PARAMS` in `src/lib/sim/navigator.ts`). The agent
passes a recipe's settings to `plan_steps` in one call and the replica plays them;
`src/lib/sim/recipes.spec.ts` runs every recipe on a new project, on the track its steps name, and
fails when a setting cannot be reached. Values are starting points (`confidence: derived`), not
measurements.

## Workflow

```sh
node scripts/build-manual.mjs              # validate everything, write build/ (+ coverage summary)
node scripts/build-manual.mjs --coverage   # also list every guide section no unit cites yet
node scripts/build-manual.mjs --check      # CI-style: fail if build/ is stale (writes nothing)
node scripts/build-manual.mjs --allow-dangling   # related ids of units not written yet → warnings
pnpm exec vitest --run --project server src/lib/manual
```

To add or change a unit:

1. Pick a section from `--coverage` (it prints TE's title and size for each uncovered URL). Read it
   in `knowledge/official/guide/NN-*.md`, plus changelog entries after 1.1.15 for that feature and
   the relevant `docs/research/` notes (device facts beat the guide).
2. Write `units/<area>/<slug>.md` in your own words. Plan `related` ids with the other authors.
3. Run the build and fix every error (schema, key grammar, sources, firmware tags, verbatim runs).
4. `pnpm exec prettier --write knowledge/manual/units`, rebuild, run the tests.
5. Review: every fact true for OS 1.1.33? Anything newer than the guide tagged? Uncertain gestures
   marked? No sentence traceable to TE's wording?
6. Commit the unit **and** the regenerated `build/` together — a test fails when they disagree.

Without the scrape (fresh clone, CI) the build still validates everything except guide anchors,
the verbatim guard and coverage, and it leaves `coverage.json` as committed. Authoring needs the
scrape: `node scripts/ingest-guide.mjs`.

**Fan-out.** Parallel authors take one area batch each, agree on unit ids first, build with
`--allow-dangling` while other batches are in flight, and the final integration builds strict.

### verbatim-allow.json

A rare escape hatch for word runs that cannot be reworded (e.g. a fixed list of names in TE's
order). Each entry needs a reason and a reviewer's agreement:

```json
[{ "phrase": "exact words that may match", "reason": "why they cannot be reworded" }]
```

## Using the manual in the app

`src/lib/manual/index.ts` is the runtime API: `loadManual()`, `getUnit(id)`, `resolveRef(ref)`,
`searchManual(query, { limit, area })`, `manualPromptBundle()`, `manualCoverage()`. The agent cites
units as `[unit-id]` and facts as `[unit-id#fact-id]`, and sends users to each unit's
`official_url` for TE's original.
